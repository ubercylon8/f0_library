## The BYOVD PPL-Bypass Chain Explained

KslKatz weaponizes **KslD.sys**, a legitimate Microsoft-signed Defender kernel
driver, as the BYOVD vehicle. Because the driver is Microsoft-signed and there is no
fix, it loads cleanly under Driver Signature Enforcement and HVCI.

1. **Service reconfiguration (T1543.003).** The KslD service config under
   `HKLM\SYSTEM\CurrentControlSet\Services\KslD` is editable by any local admin and is
   **not** covered by Defender tamper protection. KslKatz redirects `ImagePath`
   (via `ChangeServiceConfigW`) toward the vulnerable 333 KB KslD.sys located outside
   the protected `\drivers\wd\` path.
2. **Trust tampering (T1112).** The driver gates access with a **plain-string
   comparison** against an `AllowedProcessName` registry value (an NT device path).
   KslKatz writes its own image's NT device path there, defeating the actor check with
   no further verification. **This is the primary, highest-confidence detection
   signal** called out in the source article: a non-Defender executable writing
   `AllowedProcessName` under a KslD service key.
3. **Driver load + device open (T1068).** The service is started and the framework
   opens `\\.\KslD` via `CreateFileW` to drive the driver's `SubCmd 12`
   `MmCopyMemory` wrapper.
4. **LSASS read (T1003.001).** Using the kernel primitive, KslKatz performs physical
   memory reads of LSASS — **bypassing PPL entirely** because the read originates in
   kernel mode — then parses credential material with the GhostKatz/Mimikatz half.

This test reproduces the **telemetry surface** of each step without the harmful
payload: the registry writes, the device open attempt, and the user-mode LSASS
access primitive (`OpenProcess` with `PROCESS_VM_READ`) all genuinely occur.

## Attribution & Scope Caveat

**Context: exit 126 at Stage 4 requires corroboration before concluding EDR caught kslkatz.**

### Three causes for a Stage 4 access-denied — only one indicates EDR action

When `OpenProcess(lsass, PROCESS_VM_READ)` is denied while running as SYSTEM or admin,
the denial may originate from any of three distinct layers, with very different
operational implications:

| Cause | Registry / Event Indicator | Operational Meaning |
|-------|---------------------------|---------------------|
| **LSA Protection (PPL)** | `HKLM\...\Lsa\RunAsPPL` > 0 AND/OR WinInit Event ID 12 "protected process with level: N" | Platform config control. Standard OS hardening. Stops all user-mode reads regardless of EDR. |
| **Credential Guard** | `HKLM\...\Lsa\LsaCfgFlags` > 0 AND `Get-CimInstance Win32_DeviceGuard` shows VBS active | VBS-based secret isolation. Can contribute to denial independently of PPL. |
| **EDR handle-stripping** | PPL absent/0, no WinInit Event 12, no Credential Guard | An EDR kernel driver or ObRegisterCallbacks hook stripped the handle. This IS a detection/prevention action by the security product. |

Distinguishing between these requires corroborating evidence beyond the exit code alone:
- `wevtutil qe System "/q:*[System[Provider[@Name='Microsoft-Windows-Wininit'] and (EventID=12)]]" /c:1 /rd:true /f:text`
- `reg query HKLM\SYSTEM\CurrentControlSet\Control\Lsa /v RunAsPPL`
- `Get-CimInstance Win32_DeviceGuard | Select-Object -Property *`
- MDE Advanced Hunting: `DeviceEvents | where ActionType == "OpenProcessApiCall" and FileName =~ "lsass.exe"`

### What a Stage 4 exit 126 does and does NOT mean

**A 126 here means:** baseline LSASS hardening (most likely LSA Protection / PPL) is present
and stops naive user-mode reads from a non-whitelisted binary. This is the correct outcome
for a hardened endpoint and satisfies the test's detection surface (Sysmon EID 10 /
DeviceEvents `OpenProcessApiCall` still fires — the telemetry signal is generated).

**A 126 here does NOT mean:** the endpoint detects or prevents kslkatz. KslKatz's actual
bypass mechanism is its signed KslD kernel driver performing `MmCopyMemory` physical reads
from kernel mode — a path that completely bypasses PPL because the read originates in
ring 0, not ring 3. PPL only gates user-mode handle access.

**This test deliberately does not exercise the BYOVD kernel read path** (safety boundary).
Stage 3 opens the `\\.\KslD` device but issues no memory-read IOCTL. Stage 4 exercises
only the user-mode OpenProcess primitive. Validating resilience to the actual PPL bypass
(i.e., "does the endpoint detect the kernel read itself?") would require exercising the
signed-driver load and kernel MmCopyMemory path — which is out of scope for this
safety-gated test.

### Verified lab observation (WIN-81O55OA6LO0, 2026-06-01)

On the verified lab host:
- **WinInit Event ID 12 reported:** `LSASS.exe was started as a protected process with level: 4`
- **LSA Protection (PPL) level 4 is active** — this is the blocking layer
- **Credential Guard:** OFF (confirmed via `Get-CimInstance Win32_DeviceGuard`)
- **Conclusion:** the Stage 4 exit 126 is attributable to PPL (platform config), not EDR detection

Stage 4 now performs this attribution probe automatically at runtime and emits the finding
to both stdout and the result JSON's `blockedBy` field, so future runs on other hosts will
self-annotate the likely cause.
