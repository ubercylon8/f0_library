## The BYOVD PPL-Bypass Chain Explained

KslKatz weaponizes **KslD.sys**, a legitimate Microsoft-signed Defender kernel
driver, as the BYOVD vehicle. Because the driver is Microsoft-signed and there is no
fix, it loads cleanly under Driver Signature Enforcement and HVCI.

1. **Service reconfiguration (T1543.003).** The KslD service config under
   `HKLM\SYSTEM\CurrentControlSet\Services\KslD` is editable by any local admin and is
   **not** covered by Defender tamper protection. KslKatz redirects `ImagePath`
   (via `ChangeServiceConfigW`) toward the vulnerable 333 KB KslD.sys located outside
   the protected `\drivers\wd\` path.
2. **Trust tampering (T1112).** The driver gates access with a **plain-string
   comparison** against an `AllowedProcessName` registry value (an NT device path).
   KslKatz writes its own image's NT device path there, defeating the actor check with
   no further verification. **This is the primary, highest-confidence detection
   signal** called out in the source article: a non-Defender executable writing
   `AllowedProcessName` under a KslD service key.
3. **Driver load + device open (T1068).** The service is started and the framework
   opens `\\.\KslD` via `CreateFileW` to drive the driver's `SubCmd 12`
   `MmCopyMemory` wrapper.
4. **LSASS read (T1003.001).** Using the kernel primitive, KslKatz performs physical
   memory reads of LSASS — **bypassing PPL entirely** because the read originates in
   kernel mode — then parses credential material with the GhostKatz/Mimikatz half.

This test reproduces the **telemetry surface** of each step without the harmful
payload: the registry writes, the device open attempt, and the user-mode LSASS
access primitive (`OpenProcess` with `PROCESS_VM_READ`) all genuinely occur.

## Safety Posture

- **No real credential exposure.** Stage 4 acquires (at most) a `PROCESS_VM_READ`
  handle to lsass and closes it immediately. It issues **no** `ReadProcessMemory`,
  **no** `MiniDumpWriteDump`/`NtReadVirtualMemory`, parses **no** secrets, and writes
  **no** dump file.
- **No real system mutation.** Stages 1–2 write to a **sandbox-owned** service key
  (`HKLM\SYSTEM\F0RT1KA-Sandbox\Services\KslD`), never the real KslD service, and clean
  up on exit. Stage 3 drops an inert placeholder `vKslD.sys` into `ARTIFACT_DIR` and
  loads **no** real driver; the `\\.\KslD` open is open-only with no IOCTL.
- **No network egress.** The test is entirely local.
- **Bug Prevention Rule 1 compliant.** Stage `fmt.Errorf` wrappers describe the
  operation ("lsass handle open returned: ...") and never inject blame keywords;
  exit-code classification keys on OS-produced denial tokens only.
- All file drops go to `C:\F0` (binaries) / `c:\Users\fortika-test` (artifacts) per the
  framework directory rules.

## Size Justification

Final orchestrator: **11.07 MB (11,607,888 bytes) — Yellow tier.**

The size is driven by four embedded, signed, gzip-compressed stage binaries
(~1.8 MB each after `gzip -9`, down from ~3.1 MB each) plus the Go runtime in the
orchestrator. Gzip compression is wired in `build_all.sh` step 5 (verified: 3.1 MB →
1.8 MB per stage). The four stages are each anchored to a distinct, load-bearing MITRE
technique in the KslKatz chain — none is speculative — so the multi-stage architecture
is required for technique-level detection precision and cannot be trimmed without losing
fidelity. The result sits just above the 10 MB Green threshold at the low end of Yellow;
no refactor recipe would reduce it without dropping a real stage.
