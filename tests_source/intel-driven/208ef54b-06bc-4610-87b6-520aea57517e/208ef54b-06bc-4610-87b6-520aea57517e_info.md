## Description

Black Basta and access brokers routinely use legitimate, vendor-signed remote-monitoring-and-management (RMM) software — most notoriously ConnectWise ScreenConnect — as their initial hands-on-keyboard foothold instead of custom malware. This is "living off trusted software": the binary is genuinely benign, code-signed by the vendor, and often already present in the environment for legitimate IT use, so hash- and signature-based controls are structurally blind to it. The detection challenge is entirely behavioral: was this specific RMM install, service, and relay *sanctioned*, or is it an attacker-installed instance riding on trust the endpoint already extends to signed software?

This test reproduces that pattern faithfully by embedding and silently installing a **real, unmodified ConnectWise ScreenConnect MSI** (staged by the user out-of-band; see Manual Build Gate), confirming the resulting `ScreenConnect Client (<instance-id>)` Windows service, generating the outbound relay egress telemetry the agent produces on start, and then using the foothold to collect and attempt exfiltration of staged decoy data. It maps to CISA/NSA/MS-ISAC's AA23-025A advisory on malicious RMM use and the mass exploitation that followed ConnectWise's CVE-2024-1709 authentication-bypass disclosure.

## Technical Details

### Attack Flow

1. **Phase 0 — Stage Extraction**: The orchestrator decompresses and writes 3 gzip-embedded, signed stage binaries plus a cleanup utility to `LOG_DIR` (`C:\F0`). Files on disk are normal signed PEs.

2. **Stage 1 — Silent RMM Install (T1219)**:
   - Drops the embedded, vendor-signed ScreenConnect MSI to `C:\F0\screenconnect-setup.msi` (observable file write).
   - Sleeps 3s, then `os.Stat()`-checks the MSI is still present (positive-evidence quarantine detection).
   - Runs `msiexec /i <msi> /qn /norestart`.
   - Classifies strictly on positive evidence: `msiexec` code 1625 (`ERROR_INSTALL_PACKAGE_REJECTED`) → blocked (126); MSI missing after 1619/1620 → quarantined (105); success codes (0/3010) are **corroborated** by checking for a live `ScreenConnect Client (*)` service or install directory before declaring success — a bare "msiexec said success" is never trusted alone.

3. **Stage 2 — Service Creation + Relay Attempt (T1543.003)**:
   - Confirms the `ScreenConnect Client (<instance-id>)` service exists (by **service name**, not display name) via `Get-Service`.
   - If present but stopped, attempts `sc start` and re-queries.
   - Generates outbound relay telemetry: DNS resolution of `instance-placeholder.screenconnect.invalid` (RFC 2606 reserved, guaranteed non-resolving) and a TCP connect attempt to that host on port 443. Both are expected to fail — logged as benign, never classified as a block.
   - Service absent → 999 (ambiguous, install didn't land — not inferred as a block).

4. **Stage 3 — Follow-on Exfiltration (T1567.002)**:
   - Stages 4 synthetic, obviously-fake decoy files (`q3_financials_DECOY.csv`, `customer_list_DECOY.csv`, `vpn_notes_DECOY.txt`, `board_minutes_DECOY.txt`) in `ARTIFACT_DIR\shared_finance_export` (not whitelisted — EDR can observe these writes).
   - Collects them into `C:\F0\collected_export.zip`; verifies the archive survives a 3s quarantine-check window.
   - Attempts an HTTPS POST of the archive to `https://exfil-placeholder.invalid/upload` (guaranteed unreachable). Failure is expected and benign.
   - Archive quarantined after creation → 105; upload failure alone is never a block.

5. **Cleanup**: `cleanup_utility.exe` (run manually as Administrator) stops and uninstalls the ScreenConnect agent (via the dropped MSI, then via `Win32_Product` CIM uninstall as a fallback), deletes residual services, removes install/data directories, removes staged decoys from `ARTIFACT_DIR`, and removes dropped test artifacts from `LOG_DIR`.

### Key Indicators
- File system: MSI drop in `LOG_DIR`, real ScreenConnect install directories under `Program Files (x86)`, decoy files in `ARTIFACT_DIR`, collected zip archive in `LOG_DIR`.
- Process creation: `msiexec.exe /i ... /qn /norestart`, `ScreenConnect.ClientService.exe` / `ScreenConnect.WindowsClient.exe`, `powershell.exe` (service-state verification only).
- Service events: creation and start of `ScreenConnect Client (<instance-id>)`.
- Network: DNS query for an unsanctioned RMM relay hostname pattern; outbound TCP/443 and HTTPS POST attempts to non-corporate destinations.

## Detection Opportunities

1. **Unsanctioned MSI silent-install** — `msiexec.exe` invoked with `/qn /norestart` installing a remote-access-software product (`ScreenConnect Client`) not present in an approved-software baseline. Sensor: process creation (Sysmon Event ID 1 / EDR process telemetry) + command-line matching.
2. **New RMM Windows service** — creation of a service named `ScreenConnect Client (*)` (or any known RMM vendor pattern: AnyDesk, Atera, Splashtop, NinjaOne, etc.) outside a change-managed deployment window. Sensor: Windows Security Event ID 4697 / Sysmon Event ID 13 (registry) / EDR service-creation telemetry.
3. **RMM relay egress from a newly-installed agent** — DNS resolution + outbound TCP/443 from a ScreenConnect process shortly after install, to a relay domain not matching the organization's sanctioned RMM tenant. Sensor: DNS logs, network EDR/firewall egress telemetry, Sysmon Event ID 22 (DNS query) / Event ID 3 (network connection).
4. **Bulk collection into an archive followed by outbound upload** — `.zip` creation in a user-writable path immediately followed by an HTTPS POST from the same process tree as the RMM agent. Sensor: file-creation telemetry (Sysmon Event ID 11) correlated with network telemetry (Event ID 3) within a short time window.
5. **Trust-inheritance anomaly correlation** — a vendor-signed, otherwise-benign binary (ScreenConnect) exhibiting install → service → egress → archive → upload in rapid sequence is anomalous regardless of code signature; this is the core behavioral signal the test is designed to validate coverage for.

**5 distinct detection points** span process creation, service creation, DNS/network egress, and file-then-network correlation — deliberately not dependent on the ScreenConnect binary's hash or signature, since both are genuinely clean.

## Lab-Bound Observability (documented 2026-07-07 — build-gated, not defense-blocked)

Unlike a kill chain that reaches a lab and is interrupted mid-chain by a defense product (the canonical Lab-Bound Observability scenario), **this test has never executed in any lab environment.** Its build is gated behind a manual, out-of-band step: the ConnectWise ScreenConnect Windows MSI must be staged by the user at `screenconnect_embedded.msi` before `go build` can even complete (the `//go:embed` directive fails otherwise, and `build_all.sh` stops at its Step 0 gate with an explicit message). As of this writing, that MSI has not been staged, so **all three stages are simultaneously unreached** — not a partial, chain-shape-driven gap, but a total absence of execution evidence.

**Stages affected:** all — stage 1 (T1219 install), stage 2 (T1543.003 service+relay), stage 3 (T1567.002 collect+exfil).

**Blocked by:** nothing defensive — a build-time prerequisite (vendor-licensed asset not yet staged), not an EDR/AV control.

This is **not a test-design deficiency** and does **not** indicate the kill chain is unrealistic:

1. **The gate exists for licensing reasons, not fidelity reasons.** ConnectWise's redistribution terms prohibit committing the MSI to a public/shared repo; the test is designed exactly as it would run once the asset is staged, and every stage's logic has been reviewed against the real MSI/service/relay/archive/upload API surface (see 2a/2b above).
2. **Refactoring around the gate would reduce fidelity, not improve it.** The alternative — fetching the MSI from a URL at runtime, or fabricating a synthetic "RMM-like" installer — would either reintroduce a network dependency inappropriate for a controlled test or abandon the "genuinely benign, vendor-signed software" premise that makes this test valuable in the first place.
3. **This is a one-time gate, not a recurring one.** Once the MSI is staged (a single manual step), the build succeeds and every subsequent build/run cycle is fully automated — this differs structurally from a chain-shape observability gap that persists across every lab run.

## Expected Results

### Unprotected System (Code 101)
All three stages complete: the vendor-signed RMM agent installs silently, its Windows service is created and running, the relay egress attempt fires (and fails only because the destination is an intentionally-unreachable placeholder), and staged decoy data is collected and an exfiltration attempt is made. `Endpoint.Unprotected` (101) is returned.

### Protected System
- **Code 105** (`Endpoint.FileQuarantinedOnExtraction`): the dropped MSI is quarantined after write (verified via `os.Stat()` after a 3s window), or `msiexec` fails to open the package (1619/1620) with the MSI subsequently confirmed gone, or the collected exfiltration archive is quarantined after creation.
- **Code 126** (`Endpoint.ExecutionPrevented`): `msiexec` returns 1625 (`ERROR_INSTALL_PACKAGE_REJECTED`), an OS-emitted policy rejection of the install.
- **Code 999** (`Endpoint.UnexpectedTestError`): any ambiguous or benign failure — e.g., `msiexec` returns an unrecognized/environmental code with the MSI still present, the service is absent after a reported-successful install, or stage-binary extraction fails. Per Bug Prevention Rule 8, these are never misclassified as a block.
