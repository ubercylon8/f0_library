## Description

The assessment measures whether endpoint trust paths continue to accept chains associated with the eight compromised eMudhra intermediate CAs. It combines the incident's direct, Sectigo AAA cross-signed, no-Certificate-Transparency, and key-rollover chains with newly generated, harmless leaf certificates. Native validators and discovered application runtimes make real trust decisions without external network access or trust-store modification.

On Linux, OpenSSL validates 16 incident chains offline, including explicit hostname verification and historical validation times. On Windows, Schannel performs real loopback TLS handshakes for six compromised TLS keys through direct and AAA paths, `X509Chain` evaluates two rollover chains, and Authenticode evaluates **four** no-op PEs: both compromised OV code-signing keys through both direct eMudhra and Sectigo AAA chains. Both operating systems also probe PATH-discovered Node.js, Java JSSE, Python default trust, Python certifi, pip-vendored certifi, and curl, with 12 TLS cases per discovered runtime path.

The build-only generator uses the publicly recovered one-byte ECDSA CA scalars after verifying each against the corresponding CA public key. Fresh P-256 leaf keys are generated for the test; deployed binaries contain those leaf keys but not the compromised CA private keys. The Authenticode PEs contain an empty `main` function and are never executed. Each is stripped, signed, and gzip-compressed for embedding, then decompressed only into `LOG_DIR` at runtime.

A 101 result identifies residual trust that could support TLS impersonation associated with T1557 or code-signing abuse associated with T1553.002. The test itself performs no interception, executes no signed validation PE, and makes no claim that an attacker completed either technique.

## Technical Details

### Assessment Flow

1. **Initialize**
   - Create `LOG_DIR` (`/tmp/F0` or `C:\F0`), resolve the organization UUID with an explicit `unknown` standalone fallback, and generate an execution UUID.
   - Initialize Schema v2.0 logging with a 240000 ms configuration and capture basic host/user/admin context.

2. **Create a confined workspace**
   - Create `emudhra-assessment-*` beneath `LOG_DIR` and defer its removal after normal assessment completion.
   - Extract only the chain, script, Java class, or signed PE needed for each probe. Gzip-compressed PEs are decompressed in memory and written without the `.gz` suffix only beneath this workspace.

3. **Run native OS validation**
   - Linux invokes OpenSSL for seven direct, seven AAA cross-signed, and two rollover incident chains. Hostname options precede certificate operands, and operational file-loading output is explicitly inconclusive.
   - Windows invokes the PowerShell helper for Schannel TLS, offline `X509Chain` rollover validation, and four Authenticode checks.

4. **Run independent runtime validation**
   - Resolve Node.js, Java, Python, certifi, pip-vendored certifi, and curl from the active environment.
   - For each of 12 generated cases, serve the chain on an ephemeral `127.0.0.1` listener and invoke the runtime's real TLS client.
   - Set `PYTHONDONTWRITEBYTECODE=1` for Python child processes.
   - Classify only explicit successful validation as accepted and certificate-specific failures as rejected; operational and all other failures remain errors.

5. **Aggregate and persist**
   - Finalize each control independently; absent optional runtimes become skipped controls.
   - Any accepted chain produces control and overall 101. Otherwise, errors or zero assessed controls produce 999; complete rejection produces 126.
   - Close phase 0 with `success` or `failed`, including panic and timeout paths, then write `bundle_results.json`, `test_execution_log.json`, and `test_execution_log.txt` before exiting.

### Execution Context

The test primarily emulates an unprivileged validation process rather than a SYSTEM-only attack. Core probes do not require elevation and behave the same across user/admin/SYSTEM contexts; the logger records username and admin/root status for interpretation. The verified local Linux run exercised standard-user context, and the Windows lab run exercised elevated `jimx`. Windows standard-user and SYSTEM behavior have not been compared.

Optional runtime availability is part of execution context: a runtime absent from `PATH`, or certifi unavailable to the selected Python, yields a skipped control rather than a failure. The Microsoft Store Python alias is recognized as an absent runtime rather than an executable validator. This preserves result integrity but means two 126 results from different hosts may cover different runtime sets.

## Scope and Limitations

- **Discovered paths only**: PATH-available Node.js, Java, Python, and curl, plus certifi bundles importable by the selected Python. Alternate installations and custom runtime configuration are outside implicit coverage.
- **No universal application certification**: browsers, containers, custom application stores, embedded runtimes, and undiscovered stores require separate assessment.
- **Point-in-time and offline**: embedded chains and historical verification times make the test deterministic; live OCSP/CRL/CT behavior and current vendor policy are not independently queried.
- **Different validators have different semantics**: native offline chain validation, Schannel handshake policy, Authenticode trust, and runtime TLS acceptance are related but not interchangeable. Read each control's evidence.
- **Lab runtime coverage**: Windows was verified with its available native paths and curl; Node.js, Java, and Python were absent. Debian's 101 result reflects its lab configuration and is not a customer-fleet finding. No EDR detection efficacy is inferred from either result.
- **Detection boundary**: parser validation and YARA sample matches establish artifact quality, not live SIEM tenant firing. Some rules require documented custom certificate-observation telemetry or specific sensor tasks.
- **Result scope**: a compliant 126 applies only to paths actually assessed. Skipped controls and inconclusive 999/102 outcomes must not be counted as protected.
- **Attack boundary**: the test demonstrates residual trust exposure, not actual credential theft, traffic interception, malicious code execution, or SmartScreen/reputation bypass.

## Expected Results

### Exposed / Non-Compliant (Code 101)

At least one compromised chain is accepted by any assessed native or runtime path. Any acceptance takes precedence over rejection or errors elsewhere. The control evidence identifies the runtime, case, accepted count, and validator output.

### Compliant / Protected for Assessed Paths (Code 126)

Every executed probe rejects with certificate-validation evidence, at least one control is assessed, and no assessed control is inconclusive. This is a trust-compliance verdict, not evidence that an EDR prevented the test binary from running.

### Incomplete or Test Error (Code 999)

No acceptance occurred, but one or more assessed controls contain inconclusive probes, result initialization fails, an assessment panic occurs, or no path can be assessed. Missing OpenSSL on Linux produces native-control errors; absent optional runtimes instead produce skipped controls. Operational output such as `Could not open` or `no such file` is explicitly inconclusive. Errors are never converted into a protected result.

### Timeout (Code 102)

The four-minute assessment context expires. The orchestrator closes the phase as failed, emits CH-EMC-999 timeout evidence, and finalizes result/log files with exit 102. This is not a compliance verdict.

### Skipped Controls

A missing optional runtime or certifi facility sets `skipped=true`, `actual=Not applicable`, and excludes the control from aggregate assessed/pass/fail counts. Skips do not cause failure, but they reduce coverage and must be considered before comparing endpoints.

### Other Codes

Generic logger categories 105/127 represent quarantine scenarios, but this assessment's trust logic does not emit them. They must not be inferred from certificate rejection alone.
